# 附录 A · 故障速查

> **怎么用**：按你观察到的**症状**找条目，不是按原因找。
> 每条给出「怎么确认是它 → 怎么处置 → 怎么确认好了」，并指向正文的规程节。
>
> 条目格式采用 GitLab 生产 runbook 的五段式：
> Symptoms（我该翻到这里吗）→ Pre-checks（确认是它）→ Resolution（处置）→
> Post-checks（确认已解决）→ Rollback（撤销）。
>
> **编号**：`FX-<域>-<序号>`。域 = SVC 服务状态 / NET 网络可达 / CFG 配置 /
> MDL 模型行为 / AGT 助手产出 / DBG 故障定位 / BLD 链路搭建 / ORG 组织与归属。

## FX-SVC-01 · 部署完了，但改动看起来没生效

**Symptoms**
- 部署流程报告成功，但线上行为仍是旧的
- 新加的日志字段没出现；新改的文案没变；修复的 bug 仍能复现
- 服务本身可用，功能没有报错

**Pre-checks**（确认是「旧版本仍在接活」，而不是别的问题）
1. 查正在响应的实例版本标识，与本次部署的版本**逐字符**比对（VER-02.2）
   → 不一致即确认命中本条。
2. 版本一致时，转查是否**部分节点**未更新：多节点重复采样（常见误判见 VER-02）。
3. 仍一致时**不是本条**，转 FX-CFG-01（配置未生效）或 FX-SVC-02（返回内容错误）。

**Resolution**
1. 按 VER-02.3 清理旧实例：
   - 进程残留 → 用服务管理器整组回收（如 `systemctl stop`，走 cgroup），
     **不要只 kill 主进程**——子进程会被 init 收养并继续接活。
   - 编排环境 → 确认旧副本已终止，不只是「新副本已就绪」。
   - **负载均衡 → 查运行时后端表并摘除旧后端**；配置文件正确不代表运行时表正确。
2. 重新执行切换。

**Post-checks**
- 跑完 VER-02 四项，取得 `VERDICT=SWITCHED`
- 特别确认 `VER-02.4`：部署时间之后有**真实业务事件**落在新实例的日志里
- 无法验证的项按未通过处理（保守缺省）

**Rollback**
- 若新版本确认有问题：回滚后**重新跑一遍完整 VER-02**——
  回滚同样是一次切换，同样会留下旧实例。未验证的回滚不计作已回滚。

**→ 正文**：VER-02 切换验证 ｜ 相关：DEP-01、VER-05

## FX-AGT-01 · AI 助手说做完了，但产物对不上

**Symptoms**
- 助手报告了执行结果（退出码、字节数、「三个文件均正常」），而目标文件/变更不存在
- 助手随后把矛盾解释为「环境不可信」「回显被污染」「命令时灵时不灵」
- 高发位：会话被中断（报错、断连、上下文压缩）或被催促之后的**第一条消息**

**Pre-checks**（确认是「执行未发生」，而不是「执行了但失败」）
1. 走独立通道回读产物：`test -f` / 校验和 / 控制台（DIS-03.2）
   → 产物缺失，继续第 2 步。
2. 在**本轮**原始调用记录里查找产生那个结果标量的工具调用（DIS-03.3）
   → **零次相应调用即确认命中本条**（伪报，不是执行失败）。
3. 找得到调用、且有真实错误输出 → **不是本条**，属正常的执行失败，按该错误排查。
4. 记录不可访问 → **记为未验证**，按保守缺省当作未通过处理（**不等于已确认是伪报**）。

**Resolution**
1. 把该动作标记为**未执行**，就地重跑那一条（DIS-03.6）——不外推成「工具链失效」。
2. 助手已给出环境指控时，要求出示那条异常输出的原文；拿不出即判定为想象（DIS-03.5）。
3. **不要用追问代替验证**：同一个生成过程无法为自己作证。
4. 后续所有基于该结果的分析一并作废重来——包括「看起来很专业」的那些。

**Post-checks**
- 跑完 DIS-03 判定表，取得 `VERDICT=EXECUTION_CONFIRMED`
- 特别确认 `UNBACKED_SCALARS=0` 与 `ENV_BLAME_WITHOUT_EVIDENCE=0`
- 未取得 `EXECUTION_CONFIRMED` 前，不得进入 VER-05 验收

**Rollback**
- 若已在虚假前提上做过改动：逐条回退，然后从最后一次**有调用记录支撑**的状态重来。

**→ 正文**：DIS-03 AI 助手产出验证 ｜ 相关：DIS-01、DIS-02、BLD-04

## FX-NET-01 · 服务端自测正常，用户连不上

**Symptoms**
- 在服务器本机或同一内网里测，一切正常（握手成功、状态码正常）
- 用户侧连接失败、超时、或握手中途断开
- 报错常落在你最熟悉的那一层（证书、协议版本、握手），诱使你去改它

**Pre-checks**（确认是「路上被拦」，而不是服务端真的坏了）
1. 先把自测的**路径覆盖范围**写出来：这次请求从哪个位置发起、经过了哪几段。
   若答案是「服务器 → 自己」（hairpin），它覆盖不到用户与你之间的任何一段（VER-03）。
2. 换一个**真正在用户网络位置**的观测点重测（移动网络、不同地域、不同运营商）。
   两个位置结论不一致 → 命中本条。
3. TCP 通但 TLS 握手中途失败，是中间设备的典型形态，不是证书或协议协商的形态。
4. 若各位置结论一致且都失败，**不是本条**，回 VER-02 查服务本身。

**Resolution**
1. 定位被哪一段拦下：逐段（本机 → 出口 → 中间链路 → 目标）缩小范围。
2. **同时排查非工程域根因**——这类原因不出现在任何日志里，但能让整条链路失效：
   域名备案与合规状态、账号权限与配额、商品/能力的授权范围、合同与计费状态。
3. 属于非工程域的，**正确动作往往是什么都不做**（等审批/等生效），
   而不是继续改配置——错误的修复会比它试图解决的问题活得更久。

**Post-checks**
- 从**用户所在的网络位置**复测通过，而不是从服务端复测
- 明确记录本次结论的覆盖范围：写「从某位置发起的请求正常」，不写「服务端正常」
- 排查期间做过的配置改动，逐条评估是否该回退（见 Rollback）

**Rollback**
- 沿错误方向做过的改动（换证书、降协议版本、改超时）**全部回退**并记录原因，
  否则它们会在半年后变成没人解释得清的历史配置。

**→ 正文**：VER-03 可达性验证 ｜ 相关：VER-02、DIS-01

## FX-MDL-01 · 模型不遵守明确写下的指令

**Symptoms**
- 提示词里写了「必须」「禁止」，模型仍然不照做
- 加强措辞后没有改善，或只在部分场景改善
- 模型输出了上下文里提供的某个候选项，而该项并非用户真实所指
- 模型在信息不足时猜了一个，而不是承认不确定

**Pre-checks**
1. 这条要求是「要它**识别**」还是「要它**照做**」？
   给识别任务喂候选清单 = 同时给了它编造的原料（BLD-04）。
2. 指令里有没有给出**不确定时的合法出路**（反问、声明不知道、转人工）及具体话术？
   没有 → 模型会优先用手边的东西而不是承认不足。
3. 当前行为是否是某种**训练先验的自然结果**（例如格式惯例、话轮惯例）？
   是 → 加强措辞几乎必然无效。
4. 这份指令是否从别的链路/别的消费者那里迁移过来？
   → 转 BLD-04.4 逐项审隐性约定（标点、格式、顺序、字段名）。

**Resolution**
1. **不要靠加重措辞。** 改用结构性手段：改变数据形状、约束输出格式、
   移除不该给的候选集、显式提供出路话术。
2. 需要**确定性**保证的，把约束移到模型之外——输出校验、schema 校验、
   拒绝不合规输出的闸门。写进提示词的是劝导，闸门才是确定的（BLD-04、DIS-02）。
3. 存在多条互相冲突的局部补丁时，登记冲突并显式声明优先级，
   不要把仲裁推给模型。

**Post-checks**
- 用**固定输入集**重跑，统计违规率，而不是抽查一次就下结论
- 确认新加的约束没有把另一个场景改坏（补丁之间的张力）
- 若改动是加了闸门：确认闸门自身有验证（DIS-02.4）

**Rollback**
- 措辞类改动可直接回退；结构类改动回退前先确认没有下游依赖新格式。

**→ 正文**：BLD-04 模型行为约束 ｜ 相关：BLD-03、DIS-03

## FX-ORG-01 · 一件事卡住，双方都以为对方在做

**Symptoms**
- 某个事项停在原地数天，追进度时每一方都说「在等对方」或「以为对方在办」
- 高发于**非工程域事项**：域名备案、账号审批、合同盖章、合规评估——
  它们不出现在任何监控里，不产生任何技术告警
- 事发前各方的工作清单都是全绿的

**Pre-checks**（确认是「无主」，而不是「有主但慢」）
1. 对该事项跑 ROL-02.3 归属三问：谁有权限改／谁背验收／合同结束后谁维护。
   三问答不出、或答案互相矛盾 → **命中本条**。
2. 三问指向同一个明确的人、且对方确认在办 → **不是本条**，属进度问题：
   要预计完成时间与阻塞依赖，按普通排期跟进。
3. 三问指向某个**部门**而落不到人名 → 仍算命中——部门不是 owner。

**Resolution**
1. 现场指定唯一 owner：**一个名字，不是一个部门**，并请对方当场复述确认
   ——沉默不是认领（ROL-02 常见误判）。
2. 按 ROL-02.4 登记进边界登记表，补上预计完成时间与升级路径两个字段。
3. 事项属客户侧审批流的，把法定/流程时长问到手并计入排期——
   **正确动作可能是等待并调整计划，而不是绕开流程**（同 FX-NET-01 Resolution）。
4. 顺手全查：对登记表其余事项跑一遍三问，无主事项通常不止一件。

**Post-checks**
- 该事项在登记表中有唯一 owner、预计完成时间、升级路径三字段齐
- 下一次同步会上，该事项能报出**状态变化**（不是再次「在推进中」）
- 登记表中无其他三问不一致项

**Rollback**
- 不适用：本条是归属修复，无技术改动可回退。
  但若停摆期间有人为「绕开流程」做过技术改动（换域名、走临时通道），
  逐条评估回退——参照 FX-NET-01 的 Rollback 原则。

**→ 正文**：ROL-02 相邻角色边界 ｜ 相关：ROL-03、ROL-04、VER-03

## FX-ORG-04 · 什么都找你，角色被当成驻场咨询/售后

**Symptoms**
- 客户遇到任何问题第一个想到你：产品缺陷、环境故障、口径疑问、别家系统的毛病，不分归属全部涌来
- 你的时间被这些事项占满，本次交付当前阶段的工作停滞或靠挤压推进
- 涌来的事项里，大量是「只要建议」或「装完之后的看护」，而不是把既有能力部署成客户结果

**Pre-checks**（确认是「角色被误用」，而不是「交付负载正常但排期失控」）
1. 抽最近涌来的事项，逐件过 ROL-01 判定标准两问：
   成功是否以「客户目标的达成」度量？工作主体是否是「部署/适配既有能力」？
2. 两问皆是的占多数 → **不是本条**：这些本来就是 FDE 的活，属排期问题，
   按 ROL-04 的阶段正常推进。
3. 任一为否的占相当比例——只要建议不要系统、或以「装完/修完」为终点——
   → **命中本条**：你被按驻场咨询或售后支持在用（ROL-01 常见误判列出的两种误用形态）。
4. 某件事说不清在不在范围内 → 范围以 ENG 阶段双方写下的成功标准为准，
   不以任何演示或口头承诺为准（ROL-02 常见误判）。

**Resolution**
1. 对每件两问任一为否的事项跑 ROL-02.3 归属三问：谁有权限改、谁在合同里背这项验收、
   合同结束后谁维护——三问一致指向的人就是 owner，把事项移交给他。
   三问答不出或互相矛盾的，是无主事项，转 FX-ORG-01 处置。
2. owner 必须是**一个名字，不是一个部门**，并请对方当场复述确认——沉默不是认领
   （ROL-02 常见误判）。
3. 按 ROL-02.4 把这些事项登记进边界登记表，补上预计完成时间与升级路径两个字段；
   非工程域事项照登不误——它们不产生任何技术信号，登记表是唯一防线。
4. 向客户讲清分界：FDE 的交付物是部署起来的运行系统，成功以客户目标的达成度量
   （ROL-01.1 三承重件）；把 FDE 当售后/实施外包用，丢的是「现场作为产品传感器」
   的那一半价值（ROL-01 常见误判）。
5. 源头是售前展示过的，取承诺清单，在 ENG 关口把「展示过的」与「承诺交付的」
   显式切开（ROL-02.1 第二行的用途）。

**Post-checks**
- 新涌来的事项能用 ROL-01 两问一分为二：两问皆是的进 ROL-04 生命周期，
  任一为否的在登记表里有唯一 owner
- 登记表过一遍 ROL-02 判定标准清单：每项唯一 owner、三问不一致的高危项已标出、
  非工程域事项有预计时长与升级路径
- 下一次同步会上，移交出去的事项由其 owner 报状态，而不是回流到你

**Rollback**
- 不适用：本条是角色与归属修复，无技术改动可回退。
  已替别人辖区接下的存量事项不是「回退」而是「移交」——逐件走 Resolution 第 1、2 步定位 owner。

**→ 正文**：ROL-01 角色定义、ROL-02 相邻角色边界 ｜ 相关：ROL-04、ENG-02
