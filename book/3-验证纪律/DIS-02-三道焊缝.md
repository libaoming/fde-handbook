# DIS-02 · 三道焊缝：把验证从自觉变成系统

**目的**　选择用哪一档手段来保证一项验证**真的会被执行**。
本节给出三档强度递增的机制、各自的失效方式，以及一条选择判据：
**这项验证漏掉一次的代价有多大，就用第几档。**

**前置条件**

- 你已经知道这项验证要取什么证据（见 DIS-01）
- 你能判断这项验证**漏掉一次**的后果：自己多花半小时，还是客户侧发生事故

---

## 规程

### DIS-02.1　认清三档的强度差

| 档 | 机制 | 靠什么生效 | 典型失效方式 |
|---|---|---|---|
| 一 · **回读** | 声明完成之前，先对目标跑一条读取命令，拿真实输出当证据 | **人的自觉** | 赶时间就跳过；疲劳时自我豁免；换个人就没了 |
| 二 · **判定标量** | 让命令自己吐出无法含糊的结论（`VERDICT=SWITCHED`、退出码、HTTP 状态码） | **设计** | 有人不看那一行；判据本身写错 |
| 三 · **闸门** | 把验证做成流程里绕不开的关卡（hook、CI 检查、harness、评测） | **系统** | 闸门本身有 bug 却无人知晓；覆盖面有缺口 |

**判据：一档靠人记得，二档靠人看见，三档不需要人。**

这个强度差在工具侧有一个现成的例子——Anthropic 的 Claude Code 文档把它说得很直接：

> 「Unlike CLAUDE.md instructions which are advisory, hooks are deterministic
> and guarantee the action happens.」（写进指令的是劝导，hook 才是确定性的）
> ——https://code.claude.com/docs/en/best-practices
>
> 边界：该表述描述的是**给模型的指令**在 Claude Code 语境下的约束力，
> 外推到其他工具时应表述为「同类机制」。**它本身并不涉及组织流程。**

**而写给人的流程要求同样只有第一档强度——这是本手册的判断，不是上述引文的结论。**
理由不依赖任何厂商口径：一条要求只有在「不执行就走不下去」时才具备确定性，
而写在文档里的要求永远可以被跳过。

### DIS-02.2　第一档：回读怎么算数

回读的最小形态：**做出完成声明的同一轮里，必须有一条真跑过、
其输出能支撑这句声明的读取命令。**

三条落地要求：
1. 读的是**目标本身**，不是你刚才写它的那个动作的回显——
   写入操作的回显只证明「这次调用写了盘」，不证明终态如你所想；
2. 声明里出现的每一个具体值（路径、行数、条数、是否存在），都必须来自命令输出，
   不许凭记忆或推断填；
3. 回读结果与预期矛盾时，**先改自己的记录，不要先怀疑环境**（理由见 DIS-03）。

### DIS-02.3　第二档：把判定权从人手里拿走

**不要让人去读三段输出然后自己下结论。** 让脚本直接输出判定标量：

```
SERVICE_ACTIVE=yes
VERSION_MATCH=yes
STALE_INSTANCES=0
VERDICT=SWITCHED
```

这样做的收益有两层：人不必解读，因此不会解读错；**更重要的是，
一个明确的标量很难被含糊转述**——「看起来是好的」可以糊弄过去，`VERDICT=NOT_SWITCHED` 不行。

设计要求：
- 判定标量必须是**穷尽的**——每种输入都能落到一个确定值，不能有「没输出」的情况；
- 无法判定时输出显式的 `UNKNOWN` 或 `SKIPPED`，**不要默认输出通过**（fail-closed）；
- 每个标量旁边给出它**排除了什么**，否则读者会高估它的覆盖面。

### DIS-02.4　第三档：闸门，以及它一定有的缺口

闸门是唯一不依赖任何人配合的档位。常见形态：提交前钩子、CI 必过检查、
会话收尾钩子、发布流水线的强制关卡、自动评测。

**但每一道闸门都有覆盖缺口，而缺口必须被写下来。**
一个你不知道它漏什么的闸门，比没有闸门更危险——因为它会给你安全感。

对每道闸门强制回答三个问题：
1. 它**拦什么**？（触发条件的确切定义）
2. 它**拦不住什么**？（已知缺口，逐条列出）
3. 它自己**怎么被验证**？（闸门失效时，你怎么发现）

第三条不是多余的。护栏本身可能有 bug 而「通过」了——它只是没执行
（见案例 PM-07）。**没有自检的闸门，等于把信任转移到了一个没人检查的地方。**

### DIS-02.5　按代价选档

| 这项验证漏掉一次的后果 | 用第几档 |
|---|---|
| 自己返工，不外溢 | 一档（回读）足够 |
| 会误导他人的判断，或写进对外交付物 | 二档（判定标量） |
| 影响客户生产、涉及数据/资金/权限，或**你已经在这上面栽过一次** | 三档（闸门） |

最后半句是关键：**同一个错误犯第二次，说明它不适合靠自觉。**
把它升到闸门，而不是提醒自己下次注意。

## 常见误判

**「我们已经写进规范了」**
写进文档的是第一档，不管文档写得多严厉。措辞强度不改变机制强度。

**「加了检查，所以不会再漏」**
检查存在 ≠ 检查被执行。CI 里存在一个测试文件，和它在这次提交里真的跑过并通过，
是两件事——**验收锚点是那一次的执行输出，不是那个文件的存在**。

**「闸门通过了，所以没问题」**
闸门只证明它检查的那部分没问题。把闸门的通过读成整体的通过，
是把局部覆盖当成了全覆盖——同 VER-03 里「本机自测通过」的错误结构。

**「先靠自觉，出问题再加自动化」**
这个顺序本身不错，但它有个前提常被忽略：**你得真的记录下每次「靠自觉」的失败**，
否则永远等不到那个「出问题」的信号（见 DIS-04 事故台账）。

## 判定标准

为一项验证选定档位后，按下表自检：

```checklist
CHECK=<这项验证的名字>
COST_IF_MISSED=self | others | production
TIER=1 | 2 | 3                # 依 DIS-02.5，不得低于代价对应档
TIER_JUSTIFIED=yes            # 低于建议档位时必须写明理由
SCALAR_OUTPUT=yes | n/a       # 二档及以上：是否有明确判定标量
FAIL_MODE=closed              # 无法判定时是否默认不通过
GAPS_DOCUMENTED=yes | n/a     # 三档：已知缺口是否已写下来
GATE_SELF_CHECK=yes | n/a     # 三档：闸门自身怎么被验证
VERDICT=SUFFICIENT
```

> **保守缺省**：`COST_IF_MISSED` 拿不准时按更高一档处理；
> `FAIL_MODE` 必须是 `closed`——判不出来时输出「未通过」，绝不输出「通过」。

## 案例证据

> ### 案例 PM-07 · 公开事故复盘｜Meta，事故 2021-10-04（复盘 2021-10-05）
>
> 一条本应被审计工具拦下的命令执行了下去，随后骨干网路由被撤除。
>
> 官方复盘原文：「Our systems are designed to audit commands like these to prevent
> mistakes like this, but **a bug in that audit tool prevented it from properly
> stopping the command.**」
>
> **这是三档闸门的标准失效形态**：闸门存在、部署到位、且「通过」了——它只是没执行。
> 缺的是 DIS-02.4 的第三问：**闸门自己怎么被验证。**
>
> 同一次事故还留下了另一半教训：路由撤除后「it was not possible to access our data
> centers through our normal means because their networks were down」——
> 补救通道与故障共用了链路。**闸门与验证工具都不该与被保护对象共享失效域。**
>
> 出处：https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/
> ｜不可外推：这是一次内部命令误发加审计工具 bug，不能据此论证 BGP 或 DNS 的设计缺陷。

> ### 案例 · 合成示例（教学场景，非真实事故）
>
> 某团队要求「合并前必须跑一次端到端冒烟测试」，写在贡献指南里（一档）。
> 半年后统计发现，紧急发布时这一步几乎总被跳过——**恰恰是最需要它的时候。**
>
> 改法不是把措辞加重，而是升档：把冒烟测试接进流水线并设为合并的必过项（三档），
> 同时把它的缺口写在旁边——它只覆盖主流程的成功路径，不覆盖权限与配额类失败。
>
> ⚠️ **本例为本手册构造的教学场景，不是真实事故记录**，不含任何真实读数。
> 它要说明的是 DIS-02.5：**同一类失败反复出现，说明档位选低了，不是提醒不够。**
