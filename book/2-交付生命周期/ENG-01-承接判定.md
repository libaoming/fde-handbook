# ENG-01 · 承接判定：这活能不能接

**目的**　在任何人签字之前回答三个问题：这个问题**有没有界**、红线在哪、
现在拒绝和改范围还来得及吗。承接阶段做错的决定不会在承接阶段暴露——
它会伪装成 BLD 的技术困难、VER 的验收扯皮和 HND 的无人接盘，在最贵的时候结账。

**前置条件**
- 有明确的对手方与诉求（哪怕诉求还很模糊——本节的一半工作就是把它变清楚）
- ROL-01 判定标准的两问已过：这确实是一个 FDE 交付，不是定制开发或纯咨询

---

## 规程

### ENG-01.1　把立项理由改写成一个可证伪的赌注

立项论证有两种形态，**只接受第二种**：

| 形态 | 例子 | 问题 |
|---|---|---|
| 不可证伪的愿景 | 「AI 应该能帮上客服团队」 | 永远吵不完，也永远无法验收 |
| 可证伪的赌注 | 「该团队 80% 的工单集中在 12 类问题上，其中 9 类有标准处理路径，agent 应能自主处理这 9 类」（示意数字） | 数字错了当场就能证伪；数字对了，验收标准已经在里面了 |

参照系是 Meta 内部 agent 的立项方式（他们的自述）："We had a specific hypothesis that,
given 88% of queries by Data Scientists on any given day rely solely on tables queried
in the preceding 90 days, an AI agent could perform these routine data analysis tasks
autonomously." ——并明确对比了两种形态："This wasn't a vague "AI could help with
analytics" pitch, it was a specific, measurable hypothesis based on data."

**动作**：把客户的诉求改写成一句「因为数据 X，所以 agent 应能做到 Y」。
写不出 X → 先去做 ENG-01.2；写出来了 → 它就是 ENG-02 成功标准的母句。

### ENG-01.2　先算集中度：问题有没有界

全域规模吓人不等于问题无界。Meta 的数仓有数百万张表，但
"any individual analyst's work typically lives within a few dozen."——
**决定可行性的是个体工作域的集中度，不是全域规模。**

**动作**：接手前先用客户自己的数据算一个集中度数字——
80% 的调用集中在多少类输入上？90% 的查询落在多少张表上？
高频路径覆盖多少业务量？

- 集中度高（少数模式覆盖大多数量）→ 问题有界，赌注成立；
- 集中度算不出来（客户拿不出数据、或没有权限看）→ **这本身就是红线信号**，转 ENG-01.3；
- 算出来集中度低 → 缩范围到最集中的那一块，或不接。

> ⚠️ 可搬走的是**「先算这个数」这个动作**，不是 Meta 的 88% 那个数值——
> 那是他们自家群体的统计，方法未公开，不构成行业常数。
> 另注意：说服客户的数字必须来自**客户自己的数据**——
> Meta 是内部立项，说服的是自己人；你面对的客户不会认别家的数。

### ENG-01.3　红线清单：什么情况下不接或改范围

逐条核，任何一条为真且无法解除，**当场改范围或拒绝**——这是本节存在的意义：

```checklist
[ ] 成功标准无法定义：客户说不出「做好了长什么样」，且拒绝一起定义（ENG-02 无法开工）
[ ] 关键数据出不了域：勘察与验证所需的数据/日志/环境，权限明确拿不到
[ ] 非工程域死锁：备案/合规/审批类前置事项的周期长于合同期，或无人认领（ROL-02.4）
[ ] 验收权不明：没有任何一个人能代表客户签「验收通过」（ROL-02.3 三问全崩）
[ ] 赌注被证伪：ENG-01.2 算出集中度低，且客户拒绝缩范围
[ ] 期望错位无法纠正：客户要的是「效果承诺」（保证指标 X），而你能承诺的是「交付物 + 验收判据」
```

**红线不是「困难」**。困难（环境差、数据脏、排期紧）是交付的常态，进 SUR 去摸清；
红线是**结构性无解**——它不随努力改善，只随合同条款和范围改变。

### ENG-01.4　产出承接判定，走关口

承接关口的判定输出（可粘贴进过程资产，形态见 DIS-02）：

```checklist
[ ] 可证伪赌注已写成一句话，且其中的数字来自客户自己的数据
[ ] 集中度已算出并附计算口径
[ ] 红线清单逐条核过，全部为否（或已通过改范围解除）
[ ] 干系人与承接表已建（ROL-02.4），验收权落到具体人名
[ ] 成功标准草案已随赌注产出（定稿走 ENG-02）
```

任何一条不满足就进入 SUR = 把承接的缺口带进勘察——勘察只能回答「环境是什么样」，
回答不了「这活该不该接」。

## 常见误判

**「客户很有诚意，所以能做」**
诚意是合作意愿的信号，不是问题有界性的证据。诚意最高的客户往往正是问题最无界的客户
——因为他们自己也不知道要什么，所以格外需要你。诚意核对的是 ROL-02 的配合项，
可行性只认 ENG-01.2 的数字。

**「先接下来，做着做着就清楚了」**
做着做着清楚的是环境（那是 SUR 的事），不清楚的赌注做到最后仍然不清楚——
只是此时它的名字变成了「验收争议」。范围可以留弹性，**赌注不能留空白**。

**「demo 打动了客户，说明可行」**
demo 证明的是「最顺利路径在演示环境能走通」，与「该问题在客户环境里有界」无关。
把 demo 当可行性证据，等于用 BLD 最早的中间产物回答 ENG 的问题——层级用错了
（证据分级见 DIS-01）。

**「愿景大不要紧，先按大愿景签」**
签下的范围就是验收的范围。大愿景 + 小预算 = 验收时你欠客户一个愿景。
正确动作是把愿景拆出第一个可证伪赌注，签赌注，愿景写进「后续阶段」。

---

## 判定标准

见 ENG-01.4 的关口清单——它就是本节的判定标准。补一条保守缺省：
**「拿不准能不能接」按不能接处理**，回去补 ENG-01.2 的数字；
用乐观填补数据缺口，等于把证伪的机会留给交付失败。
