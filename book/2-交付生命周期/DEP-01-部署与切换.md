# DEP-01 · 部署与切换：影响清单、回退与渐进

Google Cloud 2019 年的全网降级，起点只是一次区域维护：自动化软件把「该物理位置的
任务清单」算成了包含其他物理位置网络控制任务的清单——操作者以为的作用域和实际生效的
作用域不是同一个东西（案例 PM-06）。变更的风险不在你以为要碰的范围里，而在工具实际
解析出来的范围里；本节把影响清单、演练过的回退与观测窗口做成动手前的三道关。

**目的**　把「执行变更」这个动作本身管起来：动手前知道**实际会碰到什么**，
出事时有**演练过的**退路，推进时每一步都隔着观测窗口。
本节管动作，动作完成后的验证归 VER-02——**跑完 VER-02 并拿到 `SWITCHED`，DEP 才算出关。**

**前置条件**

- BLD 关口已过：链路在客户环境跑通，丢失能力清单已确认（BLD-03）
- 本次变更有唯一版本标识（VER-02 前置条件的上游）
- 变更窗口与干系人已知会（ROL-02 登记表）

## 规程

![部署时间线：影响清单先行，分批推进隔观测窗口，异常即停走演练过的回退，SWITCHED 才出关](../figures/dep01-rollout.svg)

### DEP-01.1　影响清单先行：让工具把「实际会碰谁」打印出来

执行任何变更前，让工具**打印实际将被影响的对象清单**并人工核对——
不是你以为的范围，是工具解析出来的范围。两者的差距是一类著名事故的根源
（Google Cloud 2019 年的全网降级，起点是一次「本地」维护，引文见案例证据 PM-06）：
**作用域在逻辑层与物理层不一致，操作者看到的范围与实际生效范围不是同一个东西。**

**判据**：影响清单已打印、逐项核对过、且清单里没有你解释不了的条目。
「解释不了的条目」不是噪音，是这次变更理解不完整的直接证据——先解释，再执行。

### DEP-01.2　回退预案：没演练过的路径不计入可用能力

回退预案三问：

1. **写了吗**——回退步骤、触发条件、决策人；
2. **演过吗**——在等价环境真实执行过，含「最不敢演的那一种」；
3. **演的是这一种吗**——演练矩阵覆盖没覆盖这次变更实际依赖的路径。

第三问是 Cloudflare 2023 控制面故障的教训（引文见案例证据 PM-08）：
**「演练过」背书的只是演练矩阵里的那几格；没演过的那一格才是账单。**

**判据**：本次变更的回退路径在演练记录里能找到对应条目。找不到 → 回退能力按「未知」
计，变更方案按无退路的标准重审（更小的批次、更长的观测窗口）。

### DEP-01.3　渐进推进：批次之间隔观测窗口

- 分批推进，每批之后过一个**观测窗口**再继续；
- 窗口长度 ≥ 一个完整的配置/镜像下发周期（周期多长先问清，机理见 VER-02 的
  多节点采样判据与 PM-02）；
- 窗口内看什么：VER-01.2 里断言强度够的那些探针 + 带唯一标识的业务事件；
- **任何一批异常即停**，走 DEP-01.2 的回退——「继续推完再看」是把灰度用成了全量。

### DEP-01.4　交棒给 VER-02

切换动作执行完 ≠ 切换完成。立即执行 VER-02 四项检查，
取得 `VERDICT=SWITCHED` 才算 DEP 阶段出关。
**回滚同样是一次切换**——回滚后同样跑完整 VER-02（FX-SVC-01 的 Rollback 规则）。

## 常见误判

**「我只动了 X，所以只会影响 X」**
PM-06 的操作者也这么以为。作用域要以工具打印的清单为准，
且清单要在**执行前**看——执行后看到的那份叫事故报告。

**「高可用/回滚演练过，所以退路是通的」**
演练背书的范围止于演练矩阵（DEP-01.2 第三问）。每次变更前把「这次依赖的路径」
对到演练记录上，对不上的按无退路处理。

**「灰度了，所以安全」**
灰度的安全来自「批次 + 窗口 + 异常即停」三件套。批次之间不隔观测窗口的灰度，
只是把全量发布拆成了几次连续动作——风险原样，多了个安心的名字。

**「诊断工具肯定能用」**
PM-06 的第二课："Debugging the problem was significantly hampered by failure of
tools competing over use of the now-congested network."——诊断工具与故障共享资源时，
出事那一刻它们一起失效。这是 VER-01.1 独立性核查在变更场景的应用：
**变更前确认诊断通道与变更影响面无交集。**

---

## 判定标准

```checklist
[ ] 影响清单已打印并逐项核对，无解释不了的条目
[ ] 回退预案三问全过：写了、演过、演的覆盖本次路径
[ ] 分批推进，批间观测窗口 ≥ 一个下发周期，异常即停规则已约定
[ ] 诊断通道与变更影响面无共享依赖（VER-01.1）
[ ] 动作完成后 VER-02 已跑，VERDICT=SWITCHED
```

## 案例证据

> ### 案例 PM-06 · 公开事故复盘｜Google Cloud，2019
>
> 一次区域维护的自动化软件，把「该物理位置的任务清单」算成了包含**其他物理位置**
> 网络控制任务的逻辑集群清单，随后诊断工具与故障流量挤在同一条拥塞网络上一起失效。
>
> 官方复盘原文："The automation software created a list of jobs to deschedule in that physical
> location, which included the logical clusters running network control jobs.
> Those logical clusters also included network control jobs in other physical locations."
> 诊断工具失效一句见常见误判「诊断工具肯定能用」。
>
> 出处：https://status.cloud.google.com/incident/cloud-networking/19009
> ｜不可外推：Google 内部集群管理软件的特定 bug，不能推出「自动化维护普遍会跨区扩散」。

> ### 案例 PM-08 · 公开事故复盘｜Cloudflare，2023
>
> 高可用集群演练做过多次，唯独没演过整个 PDX-04 设施下线——而一批服务的独占依赖
> 恰好全在那里。
>
> 官方复盘原文："We had performed testing of our high availability cluster by taking each (and both)
> of the other two data center facilities entirely offline... However, we had never
> tested fully taking the entire PDX-04 facility offline."——结果一批本应高可用的服务
> "had dependencies on services exclusively running in PDX-04."
>
> 出处：https://blog.cloudflare.com/post-mortem-on-cloudflare-control-plane-and-analytics-outage/
> ｜不可外推：三设施拓扑属特例，不能推出「所有多活架构都存在隐藏单点」。
