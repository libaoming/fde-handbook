# HND-01 · 移交：能力转移的验收

**目的**　把移交做成一场**有判据的验收**：客户方在你不碰键盘的情况下，
把系统跑起来、修下去、纠错进去。移交的合格判据从头到尾只有一种形态——
**对方独立做到了什么**，而不是你交付了哪些文件（ROL-03.1 定下的原则，本节兑现它）。

**前置条件**
- VER-05 签收完成（验收 ≠ 移交，但移交以验收为前提）
- 移交资产在交付物清单中逐项有 owner 与合格判据（ROL-03）
- 客户侧承接角色实存——不存在时走 ROL-04.3 回边，回 ENG 干系人表补位，**不要硬交**

## 规程

![移交五步：分拣、runbook 客户亲手演练、知识载体三性、纠错通道有负责人、责任切换表签字](../figures/hnd01-handover.svg)

### HND-01.1　移交物分拣：方法归你，资产归客户

按 ROL-03.2 的分界线逐项分拣，移交时这刀正式兑现：

- **客户资产类**（数据语义、业务口径、强制过滤条件、累积纠错、环境配置）：
  全量移交，交到**能维护它的人**手里，并确认载体符合 HND-01.3；
- **方法类**（工作流、检查表骨架、脚本框架）：按合同约定移交副本或保留——
  在这一步发现分类有争议的项，说明 ROL-03 阶段没标干净，**当场按合同补议，
  不要含糊着交**。

### HND-01.2　runbook 演练：你在场，手不碰键盘

每份 runbook 的合格判据：**客户方指定的运维者按文档独立执行一次全流程且成功**。
执行时你在场答疑，但不碰键盘、不口头补步骤——每次你忍不住补的那句话，
就是文档里缺的那一行，**当场记下来补进文档，再跑一遍**。

覆盖底线（按交付实况裁剪）：日常启停、发布/回滚（含跑 VER-02 判定）、
告警响应（对照附录 A 的症状索引）、数据备份与恢复演练。

### HND-01.3　知识资产的载体：可 diff、可回滚、可归因

移交的知识（口径、规则、纠错记录）装进什么载体，决定了它交接后还能不能被审计。
参照 Replit 对自家实践的描述："A correction isn't a saved memory; it's a reviewed
pull request. The failing case, the fix, and the rationale are committed together;
the result is diffable, revertible, and attributable months later."
以及其对载体选择的论证："Truth in a repo isn't just versioned; it's traversable."

**判据**：知识资产的载体至少满足三性——改动可对比（diff）、可回退、可归因到人与时间。

> ⚠️ 边界与变形：Replit 是全员会用 git 的软件公司；客户的业务/数据团队多数不是。
> 「让业务方提 PR」在多数现场不可行——**变形方案的底线是有版本历史的载体**
> （哪怕是带修订记录的在线文档），死线是拒绝「口口相传 + 群聊记录」作为知识载体。

### HND-01.4　纠错通道：移交后错误怎么修进去

移交前和客户共同确定：口径错了、规则要改时，**谁提出 → 谁审 → 改进哪个载体 → 谁生效**。
理想参照仍是 Replit："New truth enters the shared corpus through code review,
not an auto-save prompt."——进入正典的东西要经过一道人工审查。

> ⚠️ 现实变形：客户团队通常没有 review 带宽（ROL-02.2 对照表）。
> 可接受的最小形态：指定**一个**口径负责人（不是委员会），改动过其手并留记录。
> 不可接受的形态：谁都能改、改了无记录——那不是纠错通道，是口径的腐烂加速器。

### HND-01.5　责任切换表与支持窗口

一页纸写清并双方签字：

```checklist
[ ] 切换日：从哪天起，一线响应归客户
[ ] 责任表：每类事件（故障/口径/账号/供应商）第一响应人与升级路径（人名，非部门）
[ ] 支持窗口：交付方的支持期限、响应口径、窗口结束后的收费方式
[ ] 遗留清单：已知未修事项与「不交付」项（ROL-03.3），逐条有归属
```

## 常见误判

**「培训做了 = 移交了」**
听课与执行隔着一整条肌肉记忆。判据是 HND-01.2 的演练——对方的手跑通过，才算数。

**「文档全了 = 移交了」**
文件送达在 ROL-03.1 里被明确排除出合格判据。没有被客户的手执行过的文档，
其完整性未经验证——写的人永远会跳过自己觉得显然的步骤。

**「有问题随时找我」**
这句好意会腐蚀掉整个 HND：它让客户永远不必真正接手，也让你的支持成本永远无法关账。
正确形态是 HND-01.5 的支持窗口——期限、口径、超期收费，白纸黑字。

**「客户团队会像软件团队一样用 git」**
不会（HND-01.3 边界）。载体选型迁就对方的真实能力，守住「有版本历史」的底线即可——
选一个对方不会用的完美载体，等于选择让知识回到群聊里去。

## 判定标准

```checklist
[ ] 移交物按方法/客户资产分拣完毕，无争议项
[ ] 每份 runbook 有客户方独立执行成功的记录（日期 + 执行人）
[ ] 知识资产载体满足三性（可 diff/可回滚/可归因），或已按变形方案落底线
[ ] 纠错通道有指定负责人且走过至少一次纠错（真实纠错，或按 HND-01.2 手法演练一次）
[ ] 责任切换表与支持窗口双方签字
```

保守缺省：某项「客户说他们会了」→ 按未验证处理，安排演练；
移交是全书最后一道关口，**在这里放水，前面所有判定标量的严格都白费。**
