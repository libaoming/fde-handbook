# ENG-02 · 成功标准：把「做好」翻译成可执行的验收判据

**目的**　在动手之前，把 ENG-01 的赌注翻译成一组**可机械执行**的验收判据，
并让双方签字冻结。交付里最贵的一类争议——「做完了」与「这不是我们要的」同时成立——
不是沟通问题，是承接阶段没有付定义成本，把它推迟成了验收阶段的利息。

**前置条件**
- ENG-01 关口已过：可证伪赌注成立、红线已排除
- 交付物清单已建（ROL-03）——判据要挂在清单条目上，不悬空

## 规程

![从可证伪赌注到判据句式，过三性检查、映射验证动作、双方签字冻结；拆不成判据的移入不承诺项](../figures/eng02-criteria.svg)

### ENG-02.1　每条判据过三性检查

一条合格的验收判据同时满足三性：

| 性质 | 含义 | 反例 → 改写 |
|---|---|---|
| **可观察** | 判据指向一个能看到的输出，不指向一种感受 | 「响应质量高」→「固定输入集 200 条上，判定标量 PASS 率 ≥ 双方约定值」 |
| **可复现** | 换一个人、换一天执行，结论相同 | 「演示时效果不错」→「验收脚本任何人可跑，输入集与判定口径入库」 |
| **有归属** | 谁执行、谁签字，落到人名 | 「客户确认后」→「由验收表中指定的验收人执行并签字」（ROL-02.3） |

**判据句式模板**：`在〔固定输入/环境〕上执行〔命令/脚本〕，得到〔判定标量〕=〔阈值〕，由〔人名〕确认。`
写不成这个句式的判据，回去继续拆——**拆不动的部分不是判据，是愿望**，
移入「不承诺项」显式声明（ROL-03.3）。

### ENG-02.2　成功标准先于一切构建

这不是本手册的洁癖，是厂商给自家用户的正式前置要求。Anthropic 的提示工程指南
开篇即声明它假定你已具备："1. A clear definition of the success criteria for your use
case, 2. Some ways to empirically test against those criteria... If not, spend time
establishing that first."——**连写提示词都要求先有成功标准与实证测试手段**，
整场交付更没有豁免。

落到流程上：ENG-02 的判据定稿之前，BLD 不开工。
先搭起来再定标准的项目，标准必然长成「现状的描述」（ROL-03 常见误判），
而现状永远通过对自己的描述。

### ENG-02.3　每条判据指到一个验证动作

判据不能停在纸面——每条必须映射到 VER 部（或第 3 部）的一个具体检查，
否则验收当天没有人知道怎么执行它：

| 判据类型 | 映射到 |
|---|---|
| 「新版本在服务真实流量」 | VER-02 四项检查（`VERDICT=SWITCHED`） |
| 「用户从他的网络位置可用」 | VER-03 可达性验证 |
| 「输出质量达标」 | 固定输入集 + 判定标量（DIS-02；golden 集的定义与归属见 ROL-03.1 验证资产） |
| 「AI 助手产出可信」 | DIS-03 判定表（`EXECUTION_CONFIRMED`） |
| 「客户能独立运维」 | HND 移交判据（按 runbook 独立执行成功） |

映射不到任何检查的判据，两种处理：为它补一个可执行检查（进 kit/ 或附录 B），
或降级为「非验收项」——**不允许存在「验收时再想办法测」的判据**。

### ENG-02.4　冻结、签字、登记变更

- 判据表放进交付计划（模板见附录 C · C-01），**双方签字后冻结**；
- 此后增删改走显式变更并记录（同 ROL-03.3 的清单纪律）；
- 验收只对「冻结版 + 变更记录」执行——**对着记忆验收 = 对着各自的记忆吵架**。

## 常见误判

**「验收标准最后再谈，先干活」**
最后谈的标准只有两种下场：长成现状的描述（永远通过，客户不认），
或长成客户临场的期望（永远不通过，你不认）。两种都比「现在就谈」贵。

**「客户满意就是标准」**
「满意」不可观察、不可复现、无归属，三性全违。它是目标，不是判据——
判据是那些你能指着说「这几条全绿，按约定即为满意」的东西。
客户拒绝把满意翻译成判据时，回 ENG-01.3：这是「期望错位无法纠正」红线的早期形态。

**「演示效果就是标准」**
演示是在最顺路径、最熟数据、你自己的操作下发生的——三个条件在验收现场一个都不成立。
用演示锚定期望，等于给验收埋一个必然的落差。

**「判据越多越安全」**
判据的成本在执行。五十条没人跑得完的判据 = 实际上没有判据，
验收会退化成抽查与谈判。**宁可十条每条都真的会被执行**——覆盖不了的风险
写进「不承诺项」，而不是稀释进判据表。

## 判定标准

```checklist
[ ] 每条判据通过三性检查（可观察/可复现/有归属），且符合判据句式
[ ] 每条判据映射到 VER/DIS 的一个具体检查或 kit 脚本
[ ] 拆不成判据的期望已移入「不承诺项」并显式告知客户
[ ] 判据表双方签字冻结，变更机制已约定
[ ] 判据总量控制在验收当天能全部执行完的规模
```

保守缺省：某条判据「应该测得了」但现在说不出怎么测 → 按映射缺失处理，
定稿前补上或降级——**验收手段的空白到了验收那天只会更大**。

> ### 案例 · 合成示例（教学场景，非真实事故）
>
> 验收会上，系统按判据表全数通过，客户负责人却说：「功能是都有了，
> 但和我们当初想的不一样。」追溯发现：当初的「想」只存在于售前演示留下的印象里，
> 从未被写成判据；而判据表是交付方在 BLD 中期单方面整理的，客户从未签字。
> 双方都没有说谎——他们验收的是两份不同的合同，其中一份没有字。
>
> 本例说明 ENG-02.4 为什么要求**双方签字冻结**：判据表的效力不来自它写得多好，
> 来自它是两边同一份。
>
> ⚠️ **本例为本手册构造的教学场景，不是真实事故记录**，不含任何真实读数。
