# SUR-01 · 环境与语义勘察：把「客户说的」换成「验证过的」

**目的**　在动手搭建之前，把客户环境的**事实**（不是客户的描述）和数据的**口径**
（不是字段的名字）摸清并落成清单。勘察阶段省下的每一个小时，
都会在 BLD 阶段以「怎么和说好的不一样」的形式加倍偿还。

**前置条件**
- ENG 关口已过（承接判定与成功标准草案在手——勘察是去验证赌注的前提，不是去闲逛）
- 已拿到进入环境的最小权限（拿不到 → 先回 ROL-02.4 登记为阻塞项，别用「先远程问答」凑合）

---

## 规程

### SUR-01.1　环境清单：每项都要「验证过」标记

逐项摸清并记录，**每项标注「验证方式」**——跑过的命令、看过的界面、拿到的输出。
只有客户口头描述的项，标 `⚠️ 未验证`——它们不算已勘察的事实，
须按本节判定标准的保守缺省处理（显式标注 + 在 BLD 设计里补防御）：

| 域 | 要摸清的 | 最低验证动作 |
|---|---|---|
| 访问路径 | 怎么进（堡垒机/VPN/物理到场）、谁批、多久 | 亲自走通一次全程 |
| 权限 | 你的账号实际能读什么、写什么、跑什么 | 逐项试探边界，记下第一个 403/denied |
| 网络 | 出网能力、内部分段、代理、被拦截的域 | 从目标机器实测（VER-03 的路径覆盖思路） |
| 部署形态 | 服务怎么起、谁管生命周期、发布怎么走 | 看一次真实的重启/发布过程 |
| 可观测性 | 有没有日志/监控、在哪、你能不能看 | 亲手查到一条业务日志 |
| 数据 | 数据在哪、量级、更新方式、能不能出域 | 跑一条真实查询并记录耗时 |

### SUR-01.2　声明与实现分离：文档描述形状，代码才描述含义

**客户环境里的一切文字都是声明：schema、数据字典、接口文档、字段命名、
「canonical」标记。声明与实现长期漂移，且漂移不产生任何告警。**

OpenAI 对自家数仓的一手描述（他们尚且如此）："Schemas and query history describe
a table's shape and usage, but its true meaning lives in the code that produces it.
Pipeline logic captures assumptions, freshness guarantees, and business intent that
never surface in SQL or metadata."

**动作**：对交付要依赖的每个关键对象（表、接口、配置），
勘察对象必须包含**生成它的那段代码或流程**，不止它的描述。
拿不到生成侧代码的，把该对象降级为 `⚠️ 仅声明可信`——
后续所有基于它的设计都要多留一道运行时验证（VER）。

> ⚠️ 边界：OpenAI 能让 agent 爬自家代码库；在客户现场，**拿到 pipeline 源码
> 本身就是要在 ROL-02.4 登记的权限项**——这正是把这条写进勘察清单的原因。

### SUR-01.3　近似重复与口径清单

同一个业务概念在客户环境里通常有多个近似载体——几张相似的表、两个版本的接口、
新旧并存的配置。它们的差别落在**口径**上，而口径不在 schema 里。
OpenAI 引用的内部用户原话："We have a lot of tables that are fairly similar,
and I spend tons of time trying to figure out how they're different and which to use.
Some include logged-out users, some don't."

**人分辨不出的，模型同样分辨不出——但模型不会说「我分不出」，它会挑一个用。**

**动作**：产出「近似重复清单」：每组近似对象一行，列出各自口径
（含不含某类数据、更新频率、谁在维护、哪个是权威）。
**问不出哪个是权威的组，整组标高危**——这是 BLD 选型时的第一批雷。

### SUR-01.4　最先要的资产：自然沉淀，而不是「请客户写文档」

请客户为你补文档，在多数现场等于没有下文——不是不配合，
是没人有产出文档的带宽（ROL-02.2）。**优先索要人干活时自然沉淀的资产**，
它们不需要任何人额外投入：

| 资产 | 沉淀自 | 价值 |
|---|---|---|
| 查询历史 | 分析师日常工作 | 真实的高频对象与用法（Meta 用它做 agent 冷启动上下文："Offline LLMs process every query an employee has run, generating descriptions of the tables they use..."） |
| 工单/客服记录 | 支持流程 | 真实的问题分布（ENG-01.2 集中度的原料） |
| 发布记录 / 变更单 | 运维流程 | 环境实际的变更频率与方式 |
| 聊天记录里的口径讨论 | 团队协作 | 口径争议的一手现场（SUR-01.3 的原料） |

Meta 说明了为什么这类资产珍贵：分析师的工作 "rarely gets committed to a repository.
Instead, it lives scattered across query editors and notebooks, invisible to any system
that might learn from it."——**最有价值的知识恰好在最不正式的载体里。**

> ⚠️ 边界：Meta 有统一查询平台可全量回捞；客户环境有没有集中的历史、
> 你能不能拿到、拿多久——是勘察要单独确认并登记的权限项，不可假设。

### SUR-01.5　勘察产出物与关口

```checklist
[ ] 环境清单：每项有「验证方式」，未验证项显式标注且已评估影响
[ ] 声明降级表：仅声明可信的对象清单（SUR-01.2）
[ ] 近似重复清单：每组含各自口径与权威判定，无权威的组标高危（SUR-01.3）
[ ] 自然沉淀资产清单：每项标「已到手 / 已登记权限申请」（SUR-01.4）
[ ] 非工程域阻塞项已按 SUR-02 单独勘察并登记
[ ] ENG-01 的赌注经勘察复核仍然成立（不成立 → 走 ROL-04.3 回边，回 ENG 重议）
```

## 常见误判

**「客户给了文档，环境算摸清了」**
文档是声明（SUR-01.2）。以文档为准搭出来的东西，将在第一次接触真实环境时
按运行时的口径被打回——只是那时它的名字叫 bug。

**「命名和标记可信」**
`revenue` 字段不说明含不含退款，`canonical` 标记不说明它已被悄悄弃用。
命名是**人写下的意图**，会随时间腐烂且腐烂无信号。以「问出口径」为准，不以读名字为准。

**「勘察就是开几次会」**
会上拿到的全部是声明。本节每一项的验证动作都要求**亲手跑一次**——
勘察的单位是「验证过的事实」，不是「记下来的说法」。

**「环境太差，这活没法干」**
环境差是困难，不是红线（ENG-01.3 的区分）。勘察的职责是把差**量化成清单**
（缺什么权限、少什么观测、慢多少），交回 ENG 调整范围或排期——
而不是在情绪上给项目判死刑。

---

## 判定标准

SUR-01.5 清单全过才出勘察关口。保守缺省：**没亲手验证的按未知处理**——
未知不阻塞进入 BLD，但每个未知都必须在 BLD 的设计里有对应的防御
（多一道运行时校验、多一个回退路径），**不允许「假定它是好的」**。
