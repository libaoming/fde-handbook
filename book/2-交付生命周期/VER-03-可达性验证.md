# VER-03 · 可达性验证：确认用户那条路通

**目的**　确认**用户从他实际所在的网络位置出发，能够抵达服务并完成一次真实业务交互**。
VER-02 回答「谁在接活」，本节回答「活派得进来吗」——两者互不蕴含。
本节给出六项检查与一个可粘贴的判定输出。

**前置条件**
- VER-02 已输出 `SWITCHED`（正在接活的确实是本次部署的版本）
- 已知用户**实际使用**的域名、端口与协议（不是内网地址，不是绕过域名的 IP 直连）
- 至少有**两个互不相同的观测位置**可用（服务器本机之外还有一个；理想情况是用户所在网络）
- 能分层读到解析结果与握手过程（`dig`/`nslookup`、`openssl s_client` 或等价工具）
- 能查到非工程域的状态：备案主体、账号权限、配额、商品授权、计费（见 VER-03.6）

---

## 规程

六项检查全部通过才算可达性成立。**任何一项不通过或无法验证，本次可达性按未通过处理。**

### VER-03.1　先声明路径覆盖范围，再谈探测结果

**在跑任何命令之前**，把用户到服务之间的路径分段写下来，并标注本次探测覆盖了哪几段。

**一个探测结果的信息量，等于它覆盖的路径段数。不声明覆盖范围的「正常」不是结论，是措辞。**

一条典型的公网调用路径：

| # | 段 | 谁控制 | 你能不能在本机自测里覆盖它 |
|---|---|---|---|
| 1 | 用户设备与客户端网络栈 | 用户 | 否 |
| 2 | 接入网（蜂窝 / 家宽 / 客户办公网） | 运营商、客户 IT | 否 |
| 3 | 中间设备（运营商链路、CDN、企业代理、防火墙） | 第三方 | 否 |
| 4 | 你的入口（LB / 网关 / 反向代理） | 你 | 是 |
| 5 | 服务进程 | 你 | 是 |
| 6 | 依赖后端（数据库、对象存储、模型 API） | 你与供应商 | 部分 |

在服务器上 `curl` 自己的域名，叫 **hairpin 自测**（发夹弯：流量从这台机器发出，绕一圈回到这台机器）。
它覆盖第 4–6 段，**完整跳过第 1–3 段**——而 1–3 段恰恰是你控制不了、因而最可能出问题的部分。

![用户真实路径分为多段，本机自测只覆盖其中最靠近服务的一段](../figures/ch03-path-coverage.svg)

粗线段是自测覆盖范围，细线段是真实路径全长；两者画在同一横轴上，长度比就是这一项的全部论点。

**报告规范**（这一项的实际交付物）：

- ❌「服务端正常」
- ✅「从 `<观测位置>` 用 `<协议+域名+路径>` 发起的请求，于 `<时间>` 返回 `<状态>`；未覆盖 `<未覆盖的段>`」

这两句话在会上听起来差不多，在排查时是两个不同的世界。

### VER-03.2　从至少两个观测位置探测同一个端点

| 观测位置 | 命令 | 覆盖的段 |
|---|---|---|
| 服务器本机 | `curl -sv https://<域名>/<真实业务路径>` | 4–6 |
| 机房外的另一台机器 | `kit/reach-probe.sh <域名> --via <ssh 别名>` | 3–6（该机器所在网络） |
| 用户所在网络 | 手机切到蜂窝数据 / 在客户办公网内实测客户端 | 1–6 |
| 多地域 | 不同区域的云主机各跑一次，或用多地拨测服务 | 3–6（多条不同链路） |

**通过判据**：各位置结论一致，且至少覆盖到第 3 段。

**位置之间结论不一致，是中间设备的指纹，不是偶发抖动。** 全通 = 正常；全不通 = 服务端或解析问题；
**通与不通取决于从哪里发起**，说明路上有东西在按某种特征挑连接。

> ⚠️ **先确认你的观测机器自己是干净的。** 本机代理、VPN、公司出网代理会接管 DNS 与连接，
> 使这台机器的「外部探测」实际上多经过一个你没有计入的中间层。
> 快速判别：看解析出的地址是不是真实公网地址——**若落在保留段、文档段或私有段，
> 说明解析已被本机某个中间层接管**，这台机器不能用来给「用户是否可达」做裁判。

### VER-03.3　分层判读：DNS / TCP / TLS / 应用

不要问「通不通」，要问「**断在哪一层**」。四层分开测，每层的失败指向完全不同的根因族。

| 层 | 单独测法 | 断在这一层意味着 |
|---|---|---|
| DNS | `dig +short A <域名>` **与** `dig +short AAAA <域名>` 各一次；**在每个观测位置都要测并对比** | 解析结果随位置而异 → 分区解析或劫持；A/AAAA 只有一个可用 → 双栈不对称 |
| TCP | `nc -z -w5 <域名> 443`，或 `reach-probe.sh` 的 `LOCAL_TCP` | 连不上 → 路由、安全组、端口未监听 |
| TLS | `openssl s_client -connect <域名>:443 -servername <域名>` | TCP 通而 TLS 断 → 见下方判据 |
| 应用 | `curl -w '%{http_code}'` + **断言响应体关键字段** | 状态码对而内容错 → 见 VER-03.4 |

> ⚠️ **双栈不对称是「部分用户连不上」的常见一类**：`dig` 默认只出 A 记录，
> 而 `curl`／`nc` 可能自行选中另一个地址族——三个工具很容易在测不同的东西。
> 两个地址族各测一次，并在结论里写明测的是哪一个。

**TCP 能连上、TLS 握手却断在中途，指向中间设备，而不是证书或协议协商。**
连接已经建立，说明路由与端口都是通的；握手在完成之前被打断，说明有第三方在这两个动作之间介入。

机理在于 SNI（Server Name Indication，客户端在握手第一个包里声明「我要连哪个域名」）是**明文**的：

> IETF RFC 8744 原文："The SNI extension is carried in cleartext in the TLS 'ClientHello' message."
> ／「SNI 扩展在 TLS ClientHello 消息中以明文携带。」
> 出处：https://www.rfc-editor.org/rfc/rfc8744.html
> ｜不可外推：这描述的是 ECH（Encrypted Client Hello）普及之前的现状，ECH 正在改变这一点。

> Cloudflare 的通俗补充："The problem is that SNI leaks to the network the identity of the origin
> server the client wants to connect to… it is the clearest signal of which server a given client is
> communicating with." ／「SNI 向网络泄漏了客户端想连接的源服务器身份……它是『客户端在与哪台服务器
> 通信』最清晰的信号。」
> 出处：https://blog.cloudflare.com/encrypted-client-hello/
> ｜不可外推：厂商博客，立场是推广 ECH；可用于说明 SNI 的可见性，不可据此论断任何具体网络的拦截策略。

两条合起来给出一个操作性结论：**任何在链路中间的设备，都能在证书出场之前就知道这条连接要去哪个域名，
并据此单独掐掉它。** 因此「握手失败」这个报错所在的层，与根因所在的层可以完全无关。

> ⚠️ 测 TLS 时必须显式带 `-servername`。不带 SNI 的握手与带 SNI 的握手可能被区别对待，
> 省掉这个参数等于测了一条用户不走的路。

### VER-03.4　断言的是业务响应，不是端口活着

**通过判据**：用**真实业务路径 + 真实鉴权 + 真实载荷**打一次请求，同时断言
①状态码 ②响应体中的关键字段。两者都对才算通过。

端口可连、进程健康、HTTP 200，三者可以同时成立而内容是错的（PM-03）。

### VER-03.5　补救通道单独验证，且不与业务链路共享依赖

**通过判据**：存在至少一条**不经过被验证链路**的访问方式（带外管理口、控制台串口、独立网络的跳板机），
并且在本次验证中**实际用过一次**——不是「理论上有」。

未使用过的通道不计入可用能力。理由见 PM-07：机器全部健在，只是路由撤了，
结果连进场维修的路一并断掉。

### VER-03.6　非工程域阻塞清单

**有些根因不产生任何日志。工程手段用尽也碰不到它们，因为它们根本不在工程域里。**

| 域 | 具体项 | 去哪查 | 典型表现 |
|---|---|---|---|
| 合规 | 域名备案与接入、内容审核、数据出境 | 备案主体控制台、接入商工单 | 特定地区或特定端口不可达，其他地区正常 |
| 权限 | 账号权限、子账号策略、密钥作用域 | 云控制台 IAM | 报「资源不存在」而非「无权限」，把人引向代码 |
| 配额 | QPS、并发数、存储、token 额度 | 控制台配额页 | 按比例失败、间歇性失败，重试有时能过 |
| 商品授权 | 模型 / 音色 / 功能属于未购买的商品 | 订单与商品清单 | 报「资源不匹配」，看起来像参数写错了 |
| 计费 | 欠费、试用到期、支付方式失效 | 账单页 | 整条链路在某个时刻突然一起失效 |
| 客户网络策略 | 出网白名单、防火墙策略、代理证书注入 | 客户 IT | 只有客户办公网不通，别处全通 |

**通过判据**：六行逐行标注「已确认无阻塞」或「存在阻塞 + 预计解除时间」，不留空行。

这六项应当在**勘察阶段就问清并留档**（见 SUR 阶段）。拖到验收阶段才发现，
代价不是发现得晚，而是在此之前所有的工程排查都白做——**并且很可能已经改坏了几处本来正确的配置。**

## 常见误判

**「服务器上 curl 通了，所以服务端没问题」**
这句话省略了主语的位置。它成立的前提是「自测走的路 == 用户走的路」，而这个前提通常为假。
Google SRE 把两类监控明确分开：黑盒是「以用户所见的方式测试外部可见行为」，
白盒是「基于系统内部暴露的指标」（*Site Reliability Engineering*, Ch.6）。
**hairpin 自测是白盒手段披着黑盒的外衣**——它从外部接口发起，却站在系统内部的位置。

**「报错说 TLS 握手失败，所以问题在证书或协议协商」**
报错出现的层，与根因所在的层，是两回事。更麻烦的是：握手层恰好是你有工具、有权限、
能立刻动手的一层。**熟悉的层会吸走注意力**——你会因为「这一层查得动」而误以为「问题在这一层」。

**「上一个假设被证伪了，那就试下一个假设」**
在同一个方向上换假设，不会走出这个方向。
**硬规矩：同一方向连续两个假设被证伪，就必须回退一层，去质疑产生这些假设的那个前提。**
（详见 VER-04）

**「先改个配置试试，反正没坏处」**
有坏处。在一个本来正确的东西上做的修改——降级证书算法、限死协议版本、关掉某项特性——
**会比它试图解决的那个故障活得更久**。真根因解除后故障自动消失，而那处没有理由的改动留在配置里，
半年后没有人记得它为什么在那儿。

**「探测过一次，通过了」**
分发通常是渐进的，同一时刻不同节点、不同链路的状态可以不同。
单点单次采样有相当概率恰好命中好的那一份，给出「已恢复」的假信号（PM-02）。**多位置、重复采样。**

**「机器全都健康，所以用户连得上」**
健康的是机器，不可达的是路径。二者可以同时为真（PM-07）。

**「返回 200，所以链路是通的」**
200 只说明有东西在应答，不说明应答的内容是对的（PM-03）。

## 判定标准

跑 `kit/reach-probe.sh <域名> --via <ssh 别名>`，判定标量直接可粘贴：

```
LOCAL_DNS=<解析到的地址|fail>
LOCAL_TCP=<ok|fail|unknown>
LOCAL_TLS=<ok|fail|skipped|unknown>
REMOTE_TCP=<ok|fail|skipped|unreachable_vantage>
PATH_COVERAGE=local_client→network→target + remote_vantage→target
VERDICT=REACHABLE
```

`VERDICT` 的取值与含义：

| 取值 | 含义 | 是否通过 |
|---|---|---|
| `REACHABLE` | 各层均通**且有第二个观测点** | 通过 |
| `INDETERMINATE_SINGLE_VANTAGE` | 本机各层均通，但只有一个观测位置 | **不通过**——单点结论不构成可达性证据 |
| `MIDDLEBOX_SUSPECTED` | 位置间结论不一致，或 TCP 通而 TLS 断 | 不通过 |
| `DNS_PROBLEM` | 解析失败 | 不通过 |
| `UNREACHABLE` | 各位置均不通 | 不通过 |
| `PARTIAL` | 有层未测（如非 443 端口跳过 TLS） | 不通过 |
| `INDETERMINATE_NO_DATA` | 采集层没拿到数据 | 不通过 |
| `INDETERMINATE_VANTAGE_UNREACHABLE` | 第二观测点连不上，该段未覆盖 | 不通过 |

**`PATH_COVERAGE` 那一行才是本节的重点。** 它强制你在看到 `ok` 的同时，看清这个 `ok` 是单点还是多点得出的——**具体覆盖到第几段，仍需你按 VER-03.1 的分段表自行标注**，脚本只区分「本机」与「有无第二观测点」；
`REMOTE_TCP=skipped` 时它只会打印单点覆盖，不会替你把没测过的路算成通过。

参考实现：`kit/reach-probe.sh`（含 20 条自测用例，覆盖判定逻辑、输入校验与 fail-closed 行为）：

```
SELF_TEST_PASS=20
SELF_TEST_FAIL=0
VERDICT=SELF_TEST_OK
```

> **保守缺省**：六项中任何一项**无法验证**（缺第二个观测位置、工具不可用、拿不到客户网络、
> 非工程域信息查不到），一律按**未通过**处理，不按通过处理。
> 两个 `INDETERMINATE_*` 判定就是这条缺省的机械形态——**「我没有数据」绝不允许被打印成「数据说没问题」。**

## 案例证据

> ### 案例 PM-07 · 公开事故复盘｜Meta，事故 2021-10-04（复盘 2021-10-05）
>
> 一次内部命令撤除了骨干网路由；数据中心的机器全部健在，对外却完全不可达。
>
> 官方复盘原文："it was not possible to access our data centers through our normal means because
> their networks were down, and second, the total loss of DNS broke many of the internal tools we'd
> normally use to investigate and resolve outages like this."
>
> **它验证了 VER-03.1 与 VER-03.5**：任何在机器上、在数据中心内部发起的检查都会通过——
> 进程活着、端口监听、本机自测全绿；而用户所在位置到服务之间的那几段已经不存在了。
> 同一份复盘还记录了护栏本身的失效：审计工具"a bug in that audit tool prevented it from
> properly stopping the command"——**它「通过」了，只是没执行。**
>
> 出处：https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/
> ｜不可外推：这是一次内部命令误发叠加审计工具 bug，**不可**用来论证 BGP 或 DNS 的设计缺陷。

> ### 案例 PM-02 · 公开事故复盘｜Cloudflare，2025-11-18
>
> 一份配置每五分钟重新生成一次，好坏交替下发，系统在恢复与崩溃之间横跳。
>
> 官方复盘原文："every five minutes there was a chance of either a good or a bad set of
> configuration files being generated and rapidly propagated across the network. This fluctuation
> made it unclear what was happening as the entire system would recover and then fail again...
> Initially, this led us to believe this might be caused by an attack."
>
> **它验证了 VER-03.2 为什么要多位置、重复采样**：单点单次探测有相当概率命中好的那一份，
> 于是「已恢复」被当成结论；而位置与时刻之间的不一致本身，才是那次故障的真实信号。
>
> 出处：https://blog.cloudflare.com/18-november-2025-outage/
> ｜不可外推：波动源于上游权限变更导致文件体积翻倍，**不可**用来论证「配置灰度本身有害」。

> ### 案例 · 合成示例（教学场景，非真实事故）
>
> 一个新上线的域名，服务端一切正常：证书有效、链完整、网关配置正确。
> 服务器本机 `openssl s_client` 握手成功，`curl` 返回 200，**全绿**。
> 但用户侧客户端一律报「TLS 握手失败」。
>
> 沿「服务端已排除，问题在客户端」这个方向可以走出一串看起来都很合理的假设：
> 换证书算法、怀疑客户端网络库版本、降级协议版本。三个假设可以逐一被证伪，
> **而方向本身从未被质疑**——因为那个全绿的自测已经把「可达性」从待办清单上划掉了。
>
> 真实形态是：链路中间的设备读取明文 SNI，按域名匹配到某条策略，
> 在 ClientHello 之后、握手完成之前掐断连接。客户端看到的现象与「证书出问题」完全同形。
> 落到 `reach-probe.sh` 的判定逻辑上，对应两条：TCP 通而 TLS 断 → `MIDDLEBOX_SUSPECTED`；
> 本机通而远端不通 → 同样是 `MIDDLEBOX_SUSPECTED`。
>
> 这类根因的处置往往**不在工程域**（见 VER-03.6），正确动作可能是等待某项资质或授权生效——
> 而这恰恰是工程师最难做出的动作：**什么都不做。**
>
> ⚠️ **本例为本手册构造的教学场景，不是真实事故记录**，不含任何真实读数、时间戳或日志原文。
> SNI 明文这一机理的出处见 VER-03.3 引用的 RFC 8744 与 Cloudflare 说明；
> 具体网络的拦截策略因地区、运营商与时间而异，本例不对任何具体网络做论断。
