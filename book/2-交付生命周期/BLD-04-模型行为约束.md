# BLD-04 · 模型行为约束：把要求落成结构与闸门

**目的**　搭建阶段，当一条要求的形态是「模型必须做 X」或「模型禁止做 Y」时，判断这条要求
该写进提示词、该改成数据与格式的形状、还是该做成模型之外的闸门；并在进入上线阶段前，
检出提示词里「写的是约束、读到的是建议」的那些写法。

> **判据：写进提示词的每一条「必须」，到了模型那里都是一个较强的倾向，不是一道闸门。**
> 它要和模型在训练中形成的先验（prior，即训练数据里学到的默认倾向）竞争。
> 冲突时胜负取决于哪一边信号更强，**不取决于措辞多重**。

**前置条件**
- 已有成功标准的清晰定义，以及针对该标准做实证测试的手段（否则本节的判定无处落地，见下方引文）
- 已知目标链路的模型形态（端到端语音 / 文本对话 / 工具调用），因为同一句话在不同形态下竞争的先验不同
- 提示词全文可读且纳入版本控制——未入版本控制的提示词无法做 BLD-04.4 的逐项审查
- 若本次是链路迁移：旧链路的提示词及其**运行形态**（谁在消费它的输出）可获取，见 BLD-03

> "This guide assumes that you have: 1. A clear definition of the success criteria for your
> use case, 2. Some ways to empirically test against those criteria... If not, spend time
> establishing that first."
> ——Anthropic, *Claude Docs* · Prompt engineering overview
> ｜https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview
> ｜不可外推：这是官方把「可实证测试」列为 prompt 工程的**前置条件**，不是对效果的承诺。

## 规程

五项检查全部通过，本节才算完成。**任何一项不通过，该约束按「未生效」处理，不得进入 DEP-01。**

### BLD-04.1　先分清「要它识别」还是「要它照做」，再决定给不给清单

对每一份要放进上下文的清单、示例、候选集、枚举，先回答一个问题：
**如果模型把这一项原样吐出来，那是正确输出，还是编造？**

| 意图 | 典型形态 | 清单该不该进上下文 |
|---|---|---|
| **要它照做** | 三个待推荐的岗位、四档价目、固定话术 | **该给**。原样复述就是正确行为 |
| **要它识别** | 可能出现的岗位词、可能的意图类别、易混词表 | **不该给**。原样复述就是编造 |

**判据：需要它识别的，别给清单；需要它照做的，才给清单。**

上下文里的任何候选集都同时是两样东西——识别的线索，和**编造的原料**。
在信息不足时，模型会优先使用手边的原料。识别类需求应改由程序侧承担：
语音识别侧的词表偏置（biasing，把候选词交给 ASR 而不是交给下游模型）、
检索、或输出之后的模糊匹配与人工确认。

**这一项排除的是**：把参考资料当成了许可。**它不能证明模型会遵守任何别的规则。**

### BLD-04.2　给出「承认不知道」的合法出路，并写明话术

一条出路必须同时包含三件东西，缺一不算：

1. **触发条件**——什么算信息不足（可判定，不能是「觉得不确定时」）
2. **动作**——反问 / 挂起 / 转人工 / 降级到固定话术
3. **话术原句**——直接给出要说的那句话，不要让模型自己想

**判据：模型编造的直接成因，通常是「猜一个」的成本低于「承认不知道」。
要做的是把后者的成本降下来，而不是禁止前者。**

反向检查同样重要，且优先级更高：**全文不得出现堵死出路的指令**——
「不要反问」「必须给出一个答案」「猜一个最接近的」「不准说不知道」。
这类句子比「没写出路」严重，因为它是在主动命令模型编造。

> "…producing plausible yet incorrect statements instead of admitting uncertainty"；
> "language models hallucinate because the training and evaluation procedures reward
> guessing over acknowledging uncertainty."
> ——Kalai, Nachum, Vempala, Zhang, "Why Language Models Hallucinate", arXiv:2509.04664
> ｜https://arxiv.org/abs/2509.04664
> ｜类型：`third-party-claim`（理论论证，非产品实测）。
> ｜不可外推：这篇论文论证的是训练与评估机制层面的成因，**不构成对任一具体模型幻觉率的量化预测**，
> 也不保证「写了出路就不编造」——它只说明了为什么「承认不确定」这条路默认更贵。

### BLD-04.3　约束优先用结构性手段，措辞排在最后一档

模型不听话时，**加强措辞通常是最低效的修法**。先问一句：
它现在的行为，是不是某种训练先验的自然结果？如果是，要找的是能压过那个先验的结构性手段。

| 档 | 手段 | 确定性 | 形态举例 |
|---|---|---|---|
| 0 | **措辞**：「必须」「禁止」「硬性要求」、加粗、感叹号 | 无。只是调高一个权重 | 「不得中途停顿」 |
| 1 | **上下文形状**：给什么、不给什么、放在哪、多长 | 无，但改变了竞争条件 | 移走识别类清单；删冗余段落 |
| 2 | **数据/文本形状**：让不该发生的事在语法上不成立 | 无，但与先验同向而非对抗 | 多条目之间不以句末标点收尾，用连接词让句子保持「未说完」状态 |
| 3 | **输出格式约束**：枚举、JSON schema、函数签名、受限解码 | 较高，取决于是否由服务端强制 | 把岗位做成枚举字段，而不是自由文本 |
| 4 | **模型之外的闸门**：程序校验、hook、拒绝不合规输出并重试或降级 | **确定** | 输出不在已知岗位表内 → 拒绝该输出，回退到反问话术 |

**判据：一条要求最终落在第几档，决定了它是约束还是建议。第 0–2 档全部是建议。**

**真正确定性的约束来自模型之外的闸门，而不是提示词本身。** 这一点有官方口径：

> "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee
> the action happens."
> ——Anthropic, *Claude Code Docs* · Best practices｜https://code.claude.com/docs/en/best-practices
> ｜不可外推：原文描述的是 Claude Code 的 hook 机制；外推到其他 LLM 应用时，
> 只能说「同类机制」（输出后的程序化校验与拒绝），不能宣称任一具体产品也有等价保证。
> 可引用的核心是官方对提示词性质的定性：**给模型的指令是 advisory（劝导性的）**。

对第 0 档的补充：措辞不仅弱，而且**加得越多越弱**——

> "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!"（同上出处）

### BLD-04.4　迁移链路时逐项审隐性约定，不只审文档

**判据：为老链路建立的约定——标点、格式、空行、顺序、字段名——从来没被当作「规则」写下来过，
所以不会出现在任何一份迁移检查清单上；而它们在新链路里的含义可能完全相反。**

审查方法不是通读提示词（读一遍发现不了，因为标点看起来根本不像一条规则），
而是**按消费者列表**：对每一类隐性约定，问「老链路里这个信号被谁消费？新链路里同一个信号被谁消费？」

| 隐性约定 | 老链路的消费者（举例） | 新链路里要核实的问题 |
|---|---|---|
| 句末标点 / 换行 | 语音合成：据此决定停顿时长 | 端到端语音模型是否把它读作**话轮结束**信号？ |
| 条目顺序 | 下游解析器按位置取值 | 新链路是否还保证顺序稳定？ |
| 字段名 | 老 schema 的键名，仅作标识 | 模型是否会据字段名推断语义（改名即改行为）？ |
| 空行 / 分段 | 模板渲染的分隔符 | 进入上下文后是否成为分段线索、影响指令归属？ |
| 全角半角、大小写 | 正则匹配 | 是否改变分词边界？ |

> 表中「新链路」一列是**必须逐项核实的问题，不是已成立的断言**。
> 它的作用是保证这些项被列出来接受检查，而不是替你给出答案。

同一份提示词在两条链路上可以同时「都是对的」和「一边是自杀开关」，
且两者不产生任何报错。**没有报错，是这一项最危险的地方。**

### BLD-04.5　补丁冲突登记，不把张力推给模型仲裁

每新增一条行为补丁，登记一行：

| 补丁号 | 要压住的行为 | 适用场景 | 与哪条已有规则冲突 | 仲裁者 |
|---|---|---|---|---|
| P-07 | 多条目播报中途停下 | 条目播报 | P-03「每句话都要有完整结束」 | ⚠️ **模型自行判断** |

**判据：当「仲裁者」这一栏填的是模型自己，这条冲突就是未决状态。**
未决冲突必须转成可判定的触发条件（写明各自适用于哪个可观察的状态），
或者把两条规则合并；两者都做不到时，登记为已知风险并在下游加闸门（BLD-04.3 第 4 档）。

不登记的后果不是某一条规则失效，而是**没人说得清哪条规则在管哪件事**——
到那时，改一句话导致另一处坏掉将成为常态，且无法定位。

## 常见误判

**「措辞已经写得很重了，它不可能不听」**
措辞的重量不是约束的强度。「必须」和「建议」在模型那里的差别是权重差别，
不是「可违背 / 不可违背」的差别。官方对提示词的定性就是 advisory（见 BLD-04.3 引文）。

**「加粗、全大写、多写几遍，遵守率会上去」**
这些手段停留在第 0 档，且与上一条同类：把一个不确定的机制反复加码，
换不来确定性，只换来更长的提示词——而臃肿本身会稀释真正的指令。

**「多给几个例子总没坏处」**
上下文里的每一份例子既是线索也是原料。判据仍是 BLD-04.1：
先问「模型把它原样吐出来算不算编造」，答案是「算」就不该给。

**「这次它照做了，说明规则生效了」**
单次通过是一次采样的结果，不是约束的证据。先验竞争的胜负是概率性的，
**验证必须重复采样**；只跑一次的绿灯没有证明力。

**「老提示词在旧链路稳定跑了很久，直接搬过来」**
稳定运行证明的是它与**老消费者**的配合正确，对新消费者没有任何证明力。
迁移必须走 BLD-04.4 的消费者列表，逐项重问。

**「加一条补丁只影响它针对的那个场景」**
补丁之间的冲突不会报错，它以「模型在某些场景下行为不稳定」的形式出现，
而这个症状指不向任何一条具体规则。冲突必须在加入时登记，事后无法反推（BLD-04.5）。

## 判定标准

五项全部通过才输出 `CONSTRAINED`。建议让脚本吐判定标量，而不是让人通读提示词自己下结论
（理由见 DIS-02）：

```checklist
RECOGNITION_LIST_IN_CONTEXT=0     # BLD-04.1  识别类清单不得进上下文
ESCAPE_HATCH_DEFINED=yes          # BLD-04.2  触发条件+动作+话术，三者齐备
ANTI_ESCAPE_DIRECTIVE=0           # BLD-04.2  堵死出路的指令数，必须为 0
ENFORCEMENT_TIER=4                # BLD-04.3  该约束最终落在第几档
IMPLICIT_CONVENTION_REVIEWED=yes  # BLD-04.4  迁移时才要求；非迁移填 n/a
UNRESOLVED_PATCH_CONFLICTS=0      # BLD-04.5  仲裁者=模型 的冲突数
VERDICT=CONSTRAINED
```

任一项为否，或 `ENFORCEMENT_TIER<=2` 而该要求属于**不可失败**的类别
（涉及金额、承诺、对外发布、不可逆动作）→ `VERDICT=ADVISORY_ONLY`，**不得进入 DEP-01**。

参考实现：`kit/soft-prior-lint.py`，检四类风险并给出判定标量。真实输出字段为：

```checklist
FILE=<被检文件>
HIT_CANDIDATE_LIST=<n>      # 候选清单（可能被当成编造原料）
HIT_PUNCT_DIRECTIVE=<n>     # 要求用标点做控制（跨链路含义反转）
HIT_TURN_END_RISK=<n>       # 多条目播报语境中的句号（⚠️ 已知噪声较高）
HIT_NO_ESCAPE_HATCH=<n>     # 缺出路，或存在明令禁止承认无知的指令
TOTAL_HITS=<n>
VERDICT=OK | SOFT_PRIOR_RISK
```

退出码：`0`=OK，`1`=SOFT_PRIOR_RISK，`2`=用法错误。自测可复现：

```
$ python3 kit/soft-prior-lint.py --self-test
...
SELF_TEST_PASS=15
SELF_TEST_FAIL=0
VERDICT=SELF_TEST_OK
```

> ⚠️ 该 linter 的 `TURN_END_RISK` 一类噪声较高（会把写给人看的说明文字报出来），
> 源码内已标注。保留它而不是删掉，是因为**一个不知道自己会漏什么的检查器，
> 比没有检查器更危险——它提供的是安全感**。它的输出是线索，不能替代 BLD-04.1–.5 的人工判定。

> **保守缺省**：一条要求若**无法在模型之外验证它被遵守**（拿不到输出、无法程序化判定、
> 没有可重复的测试），一律按**未被约束**处理：下游按最坏情况设计（人工复核、
> 拒绝该输出、或降级到固定话术），不按已生效处理。

## 案例证据

> ### 案例 · 合成示例（教学场景，非真实事故）
>
> 一条语音招聘链路里，识别准确率不佳，于是把一份岗位候选词表加进了给模型的指令，
> 意图是「让它知道可能出现哪些词，识别模糊时往正确方向靠」。
>
> 上线后出现的行为是：识别结果严重跑偏时，模型没有反问，而是**从那份词表里挑了一个
> 与错误识别结果发音接近的岗位，当作用户说过的话直接往下接**。
> 用户从未提过那个岗位——它是被亲手递进上下文的。
>
> 本例说明 BLD-04.1 与 BLD-04.2 为什么是一对：词表把「没听清」这个正确答案挤出了选项空间，
> 而指令里又没有写明「听不清该说什么」。修法不是加强措辞，是两件事——
> 把词表移出上下文（识别类需求交给 ASR 侧），并补上触发条件与话术明确的反问出路。
>
> ⚠️ **本例为本手册构造的教学场景，不是真实事故记录**，不含任何真实读数（时间戳、日志原文均无）。

> ### 案例 · 合成示例（教学场景，非真实事故）｜同一个标点，两条链路，含义相反
>
> 设想一份为「先生成文本、再交给语音合成」的链路写的提示词，其中有这样一条规则：
>
> > 句间停顿 0.6 秒（用句号或换行体现）。
>
> 同一批提示词里还配了一张标点与时长的对照表。**在那条链路里这完全正确**：
> 语音合成器读到句号会自然停顿，「想要停顿就打句号」是精确、有效、成本极低的控制手段。
>
> 迁移到端到端语音模型之后，同一个句号不再被合成器消费，而是被**模型本身**消费——
> 而模型在对话数据上学到的模式是「一句话说完，通常该把话轮交给对方」。
> 于是一条为老链路写的**节奏控制规则**，在新链路里变成了**话轮结束信号**：
> 模型念完第一项就停下来等待，而指令明明要求它连续念完三项。
>
> **它说明 BLD-04.4 为什么要按「谁消费这条规则」逐项审**：
> 这条规则通不过任何一次「把提示词读一遍」的检查，因为**句号看起来根本不像一条规则**。
> 冲突不在句子层面，在标点层面。
>
> ⚠️ **本例为本手册构造的教学场景，不是真实事故记录**，不含任何真实读数。
> 另请注意边界：「端到端语音模型在句末标点后倾向结束话轮」是一个**未经受控实验验证的机理假设**
> ——要证实它需要同内容的句号版与连接词版各跑 N 次统计中断率。
> 本例用于说明「隐性约定会随链路改变含义」这条通则，**不构成对该类模型的一般性论断**。
