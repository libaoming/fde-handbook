VER-05 · 验收与签收：判据表的执行日

目的　把 ENG-02 冻结的判据表逐条执行、留档、签字。验收不是一场会议，是一次可复现的批量验证——它的全部悬念都应该在这天之前就被消化掉：判据是冻结的、执行方式是写好的、前置检查是绿的。验收日只剩执行。

前置条件（任何一条不满足，验收日不开场） - VERDICT=SWITCHED（VER-02）：接活的确实是要验收的那个版本 - 可达性已从用户网络位置验证（VER-03） - 交付过程使用了 AI 助手的部分已取得 EXECUTION_CONFIRMED（DIS-03） - 判据表处于冻结态且双方签过字（ENG-02.4），变更记录在手

规程

VER-05.1　只对「冻结版 + 变更记录」执行

验收对象是签过字的那份判据表加上其变更记录，不是任何人的记忆，也不是现场的临时提议。会上冒出的新期望一律登记为变更申请（走 ENG-02.4 流程），不当场加入本次验收——当场加判据与当场删判据是同一种腐蚀，方向相反而已。

VER-05.2　逐条执行，逐条留档

每条判据的执行记录四个字段：

字段 要求
执行人 按判据的「归属」栏——该客户方执行的必须客户方亲手执行，你可以在旁边，不能代跑
命令与输出 原样粘贴，不摘要、不转述（判定标量的形态，DIS-02）
判定 通过 / 不通过 / 测不出——三态，没有「基本通过」
时间与环境 何时、在哪个环境跑的

「测不出」按不通过处理（保守缺省）——工具坏了、权限没了、数据缺了，都是验收环境不完备的证据，不是跳过该条的理由。

VER-05.3　不通过的处理：回边，不讨价

出现不通过项：

  1. 定位属于哪个阶段的缺口（切换问题回 DEP、构建问题回 BLD、判据本身有歧义回 ENG-02 走变更）；
  2. 修复后重跑全部相关判据，不是只补挂掉的那条（ROL-04.3 回边规则—— 修复动作本身可能弄坏已通过的项）；
  3. 不接受「这条先算过、下次补」——判据表上没有「暂计通过」这个状态。商务上要提前放行是商务决策，走的是变更（把该条移出本次范围并签字），不是把红的记成绿的。

VER-05.4　签字与证据链归档

全部判据通过后：验收单签字（签字人 = 判据表指定的验收人，ROL-02.3），执行记录整体归档进过程资产（ROL-03.1 第四类）。归档判据：半年后一个没参与过项目的人，仅凭归档能回答「当时每条是怎么过的」。

VER-05.5　验收 ≠ 移交

签收只结束了「做没做完」的问题。「客户能不能自己跑下去」是 HND 的判据（按 runbook 独立执行成功，ROL-03.1）——两者分开签，防止「验收通过」被顺手当成「移交完成」用。

常见误判

「演示式验收」你操作、客户观看的验收，验的是你的操作熟练度。判据的「归属」栏写谁执行就谁执行—— 客户方跑不动的判据，在 ENG-02 就不该写成客户方执行。

「口头通过，回头补签」没有签字的通过在下一次人事变动时清零。签字不是仪式，是把「谁认可了什么」钉进过程资产的动作。

「验收会上顺手加两条」临时加的判据没有执行方式、没有归属、没有双方共识——它们不是判据，是现场情绪。一律走变更登记（VER-05.1）。

「全绿了，项目结束了」还差 HND（VER-05.5）。验收日宣布「项目结束」是移交烂尾的标准起点。

判定标准

  • ☐四项前置全部满足后才开场
  • ☐每条判据四字段留档，判定只有三态，测不出=不通过
  • ☐不通过项走回边并重跑全部相关判据，无「暂计通过」
  • ☐验收单由指定验收人签字，证据链归档可独立复原
  • ☐已明确向客户区分：验收完成 ≠ 移交完成
