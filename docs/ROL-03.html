ROL-03 · 交付物清单：一次交付要留下什么

目的　定义一次 FDE 交付的完整产出清单。开工前用它对齐范围（这次交付会留下什么、不会留下什么），收工前用它逐项对账。防的是那种最常见的烂尾：代码跑起来了，但除了代码什么都没留下——没人能验收、没人能运维、没人说得清当时为什么这么做。

前置条件 - ENG 阶段已有双方认可的成功标准（ENG-02；没有时先回那里——清单的验收判据挂在成功标准上） - ROL-02 的边界登记表已建（清单里每项的 owner 从那张表来）

规程

ROL-03.1　四类交付物

一次交付的产出分四类。第一类人人都记得，后三类才是烂尾的高发区。

类 内容 合格判据（什么算交付了） 详见
运行系统 部署的链路、配置、基础设施变更清单 通过 VER 部全部签收判据，且变更清单与实际环境一致 BLD / DEP / VER
验证资产 验收判据、verify 脚本、golden 集（一组「输入 → 标准答案」对照对，用于回归检验）、判定标量定义 客户方能独立执行并得到与你相同的判定输出 第 3 部、附录 B
移交资产 runbook（运维操作手册）、监控与告警、责任表、知识资产 客户方按 runbook 独立执行过至少一次且成功——文件送达不算 HND-01
过程资产 交付计划、决策记录、事故台账、声明账本 第三方（新接手的人）仅凭它们能重建「为什么是现在这个样子」 DIS-04

注意合格判据的共同形态：都以「别人能做到什么」度量，不以「我写了什么」度量。这与 ROL-01.1 的定义同构——成功以客户侧可观察的结果计。

ROL-03.2　方法与客户资产的分界线

清单里每一项，标注它属于哪边：

  • 方法类：工作流、检查表、脚本骨架、分析套路——可复用到下一家客户；
  • 客户资产类：这家客户特有的数据语义、业务口径、强制过滤条件、累积的纠错记录—— 归客户，你不能带走。

这条分界线借用 Meta 内部 agent 的设计原则：“Recipes define what to do (workflows, analysis steps, response formats), but not what the data means. Data definitions belong in a separate layer called Ingredients.”——方法（Recipes）与数据含义（Ingredients）分层存放。⚠️ Meta 原文只讲工程解耦，没有提归属或合同；「方法归你、语义归客户」的归属含义是本手册的引申，引用时须保留这个标注。

为什么这刀非切不可：

  1. 归属：合同结束时哪些带走、哪些留下，逐项清楚，不用临时谈判；
  2. 维护：客户资产类必须交到客户手里维护（HND），方法类的维护责任在你；
  3. 复用合规：不切这刀，「把上家的东西用到下家」就没有安全的边界。

ROL-03.3　缺项显式化

本次不交付的项，写「不交付」并写明谁承接，不许留空。

空行有两种读法：「不在范围内」和「忘了」。收工时没有人能区分这两种—— 显式写「不交付（由客户 IT 承接监控告警）」的清单才可对账。这与 VER-02 的保守缺省同一条原则：没写 = 没做，不是「应该做了」。

同理，清单在 ENG 冻结之后的增项与删项走显式变更：记录改了什么、谁提出、为什么。默默扩充与默默缩水都会让收工对账失去基准——对账的对象永远是「冻结版 + 变更记录」，不是「大家印象里的范围」。

常见误判

「demo 通过 = 交付完成」 demo 是 BLD 阶段的中间产物，证明的是「链路能通」；它既不在验收判据里，也不满足任何一类合格判据（客户既不能独立执行，也没有留下可运维的东西）。以 demo 为终点的交付，四类资产只交付了半类。

「文档写了 = 移交完成」移交资产的合格判据是对方独立执行成功，不是文件送达（ROL-03.1 第三行）。 runbook 没被客户的手跑过一遍，你不知道它缺哪一步——写的人永远会跳过自己觉得显然的步骤。

「验收标准最后再补」收工时才写的验收标准，必然长成「现状的描述」——现状是什么，标准就是什么，于是永远通过。验收判据必须在 ENG 阶段挂在成功标准上冻结（ENG-02），清单在开工前就有「合格判据」这一列，原因在此。

「代码就是交付物，其他是官僚主义」验证资产不在清单里 → 「做完了」永远只是你的口头声明，无人能复核（DIS-01）；过程资产不在清单里 → 半年后没人解释得清任何一个配置为什么存在（FX-NET-01 的 Rollback 栏就是这种历史配置的下场）。后三类资产不是给流程交税，是让「做完了」这句话有证据。

判定标准

  • ☐清单在 ENG 阶段建立并冻结（此后增删走变更，不走默默扩充）
  • ☐四类资产每类都有条目，或显式写明「本次不交付 + 谁承接」
  • ☐每项有 owner（来自 ROL-02 登记表）、合格判据、存放位置三个字段
  • ☐每项已标注「方法类 / 客户资产类」
  • ☐合格判据全部以「别人能做到什么」表述，无一条是「我写了什么」

收工对账时逐项打勾；任何一项三字段不全，按未交付处理——清单上没有的东西，不因为「其实做了」而算数（DIS-01：无法被复核的工作等于没做）。

案例 · 合成示例（教学场景，非真实事故）

一次交付验收会上，客户负责人问：「如果你们明天全员撤场，我们靠什么把系统跑下去？」交付方能拿出的只有代码仓库和一份架构图。监控是交付方自己的账号在看，验收当时是交付方操作给客户「过目」的，业务口径的解释散在聊天记录里。系统本身没有任何故障——但按 ROL-03.1 的四类对账，交付完成度是四分之一。

本例说明清单为什么要在开工前建立：收工时才发现的缺项，每一项都要在合同尾声的时间压力下补做，而那正是最赶工、最不可能做好移交的时候。

⚠️ 本例为本手册构造的教学场景，不是真实事故记录，不含任何真实读数。
